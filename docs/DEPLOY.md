# Deployment Guide

This site deploys to **Cloudflare Workers** via `wrangler`. Every push to `main`
triggers a CI build that uploads a new Workers version without shifting traffic.
Promotion to production requires a manual approval click in GitHub.

## One-time setup (Nahar)

Before any of this can run for real, complete these steps:

### 1. Create a Cloudflare API token

1. Go to [Cloudflare Dashboard > My Profile > API Tokens](https://dash.cloudflare.com/profile/api-tokens).
2. Click **Create Token**.
3. Use the **Edit Cloudflare Workers** template (or create a custom token with:
   - **Permissions**: `Account > Workers Scripts > Edit`
   - **Account Resources**: select the account that will host the worker)
4. Copy the token immediately — it won't be shown again.

### 2. Note your Account ID

1. Go to [Cloudflare Dashboard > Workers & Pages](https://dash.cloudflare.com/?to=/:account/workers).
2. Your Account ID is in the right sidebar (or under **Overview** on the right).

### 3. Add repository secrets

Go to `https://github.com/NaharEmet/homely-site/settings/secrets/actions` and add:

| Secret name | Value |
|---|---|
| `CLOUDFLARE_API_TOKEN` | The token from step 1 |
| `CLOUDFLARE_ACCOUNT_ID` | The account ID from step 2 |

### 4. Enable the `production` GitHub Environment

Go to `https://github.com/NaharEmet/homely-site/settings/environments`:

1. Click **New environment**, name it `production`.
2. Under **Protection rules**, check **Required reviewers** and add yourself.
3. This gates the promotion step on a manual approval click in the GitHub UI.

## How deployment works

### Automatic upload (every push to `main`)

The CI workflow runs `npm run build` (which produces the Cloudflare Worker bundle
in `dist/server/`) then `wrangler versions upload`.

`versions upload` does **not** shift any live traffic. It uploads a new version
and makes it available at a preview URL. You can inspect it before anyone sees it.

### Manual promotion (after upload)

After verifying the preview, promote the version to production:

1. Go to the repo's **Actions** tab and find the most recent deploy run.
2. The `promote` job requires manual approval (the `production` environment gate).
3. Click **Review pending deployments** and approve.

The promote job runs `wrangler versions deploy <version-id> --percentage 100`,
shifting all traffic to the new version.

### Gradual rollout (optional)

For safer deploys, promote with a percentage instead of going straight to 100%.
Replace the percentage in the promote step (or run locally / in a secondary workflow):

```sh
# Shift 10% of traffic to the new version
wrangler versions deploy <version-id> --percentage 10

# After observing, increase to 50%
wrangler versions deploy <version-id> --percentage 50

# Finally, go to 100%
wrangler versions deploy <version-id> --percentage 100
```

The version ID is printed in the upload job's logs and available in the
Cloudflare dashboard under **Workers & Pages > astro-site > Versions**.

### Rollback

If the error rate regresses during the observation window:

```sh
wrangler rollback
```

This instantly reverts to the immediately-previous version (the one that was
at 100% traffic before the current deployment). No version ID is needed —
`rollback` always targets the prior version.

## Local development

```sh
npm run dev        # Astro dev server (uses the Cloudflare adapter in dev mode)
npm run build      # Produces the Worker bundle in dist/
npx wrangler dev   # Local preview with wrangler (optional, mirrors production)
```

## File overview

| File | Purpose |
|---|---|
| `wrangler.jsonc` | Stable wrangler config at repo root (checked in) |
| `astro.config.mjs` | Astro config — uses `@astrojs/cloudflare` adapter |
| `.github/workflows/deploy.yml` | CI: build + upload + gated promotion |
| `dist/server/wrangler.json` | Auto-generated by the adapter at build time (not checked in long-term) |
